# PROJECT 1 · RAG-Based Academic Document Explainer ("StructRAG")
Solo, all 9 commits mine (6 Mar–13 Aug 2026). Frontend on Vercel; backend config for Railway (live status = F8).
**Resume vs truth:** ✓ full-stack RAG app; ✓ REST API for chunking, indexing, retrieval. ⚠ "deployed": frontend on Vercel; backend reported down 27 Sep 2026 (F8), so offer a local Docker demo. **✗ "multi-turn" is NOT true:** the chat shows several questions in a row, but each is sent alone with no history ("what about its limitations?" has no referent). Say this first, then the fix: send the last N messages, or have the LLM rewrite follow-ups into standalone queries before retrieval.
**Pitch:** upload a research-paper PDF and ask questions; the backend chunks it, embeds the chunks into ChromaDB, retrieves the most relevant chunks, an LLM answers, and the response shows page-level sources. FastAPI + Python, React + TypeScript, Docker, GitHub Actions CI, plus an experimental section-aware ranking layer I haven't evaluated.
**How it works**
- **Stack:** FastAPI 0.115 + Pydantic, gunicorn with 1 uvicorn worker, Python 3.11 · pypdf (+ `unstructured` fallback) · LangChain text splitter · sentence-transformers `all-MiniLM-L6-v2` (384-dim, normalized) · ChromaDB · SQLite (jobs, documents, document_trees) · LLM providers OpenAI/Gemini/Hugging Face/**mock (default)** · React 18 + TS + Vite + Tailwind + Axios · Docker Compose (backend + Chroma server + frontend) · GitHub Actions (backend pytest; frontend lint/test/build; Docker builds); tests: 4 backend + 2 frontend.
- **Upload:** `POST /api/v1/upload` saves the PDF, creates a job row, returns **202** + job id. A background task parses pages, builds a section tree, chunks each page (**3000 chars, 800 overlap**, per page so each chunk has a page number), embeds in batches, writes vectors to Chroma and the tree to SQLite. Progress 25/50/60/80/100 in `jobs`; browser polls `GET /status/{job_id}` every second.
- **Ask:** embed question → Chroma nearest chunks (filter by `doc_id`, fetch 2×top_k) → StructRAG boost → prompt (answer only from context, else "I don't know"; temperature 0.2) → LLM → answer + sources (page, snippet, chunk id, score). top_k 1–10, default 5.
- **StructRAG:** ingestion detects headings (LLM table of contents if a real provider is set, else regex) into a **flat** list of sections with page ranges and one of 13 types (methodology, results…). At query time up to 3 matching sections are chosen; chunks on their pages get score `1/(60+rank)` × a boost of 1.0–2.0 (shrunk when few vector hits agree), plus +0.1 for the top 2 sections. k=60 is the usual RRF default.
- **API:** 9 endpoints under `/api/v1` (upload, status, docs list, docs delete, ask, explain-section, summarize, tree, tree/navigate) + `/` and `/health`; the website uses only upload, status, list, delete, ask.
- **Real engineering fixes (true challenge stories):** broken-pipe errors from forked processes in uvicorn workers → multiprocessing `spawn` + tokenizer parallelism off; sent full chunk text in the prompt instead of a short snippet; raised Gemini output limit (answers were cut off); a retired Gemini model returned 404 → added model fallback; CORS made multi-origin for the Vercel frontend; workers 2→1 (I believe for memory/in-process state; not written down).
- **Choices (say "the usual reason is…"):** FastAPI: type hints give validation + docs, ML libs are Python (alt Spring Boot/Flask). Chroma: embedded, metadata filter (alt pgvector/FAISS/Qdrant; not benchmarked). MiniLM: small, free, CPU (alt hosted/larger; not compared). 3000/800: judgement to approximate ~800-token chunks, **not tuned**. 202 + polling + background task: no extra infra (alt Celery/Redis + SSE). SQLite: zero setup (alt PostgreSQL). Mock provider: whole pipeline runs with no key, so CI needs none.
**Weaknesses (say first, then the fix)**
1. **No retrieval evaluation.** Fix: 30–50 gold questions with correct pages; compare recall@5 and MRR plain vs boosted; groundedness.
2. **Not multi-turn** (above). 3. Tree is **flat** (depth bonus never applies); regex headings mistake titles/authors for sections; `classify_query` is reported but unused; "hybrid" = vector + section boost, **no BM25**; one ranked list, so it's a structure-aware re-rank, not a true fusion.
4. **Not production-ready:** no auth (anyone can list/delete any document); ingestion runs in the web process, so a restart strands the job in "processing"; local SQLite/Chroma storage is lost on redeploy on typical free hosts; tests don't cover tree or ranking.
5. **UI bug:** boosted scores max ~0.033, so the UI "percentage" shows ~2% and the badge says "Low". 6. **Silent hash-embedding fallback** if MiniLM fails: pipeline runs but retrieval is meaningless; should fail loudly. 7. LLM errors returned as HTTP 200 chat text (should be 502/429); in-memory global rate limit (60/min per IP; 5 LLM calls/min total); weak upload validation (no size or `%PDF` check); scanned PDFs fail (no OCR); tables/equations lose structure; keyword safety filter blocks some normal questions; summary uses only 5 chunks; prompt-injection risk from PDF text; 3000-char chunks may exceed MiniLM's input limit (to verify).
**✗ NOT CLAIM:** multi-turn/memory · any accuracy/recall/"X% better" · "proven/novel/patented/patent-pending/no prior art" · production-ready, scalable, secure, multi-user · "it's live" (unless F8) · always grounded/no hallucination/100% cited · hierarchical or depth-weighted tree · intent drives retrieval · hybrid keyword+vector · handles scans/tables/equations · 3000/800 tuned · Redis/caching (Redis in compose is unused) · CI deploys or tests cover retrieval · UI has section explorer/summary · user counts/feedback · "Gemini free tier in production" · "sources prove each statement" (they are retrieved chunks).
**Concepts:** RAG = retrieve relevant text, then have the LLM answer from it (cheaper than pasting the paper, gives sources, reduces but doesn't stop hallucination). Embedding = list of numbers for meaning; cosine similarity compares direction; normalized vectors make it a dot product. Chunking: one vector per paper blurs meaning; overlap keeps boundary sentences (only within a page here). Temperature = randomness (0.2 default). RRF = sum of `1/(k+rank)` across ranked lists. 202 Accepted = work continues, client polls. Scale-up: Celery+Redis workers, PostgreSQL, shared vector DB, S3, per-user auth and rate limits, OCR for scans. Security: no auth, upload checks, prompt injection (no tools to abuse). Evaluate: gold set, recall@5, MRR, groundedness.

**Pitch:** a farmer picks Dead Heart or Tiller, uploads a photo and answers 15 yes/no symptom questions; YOLOv8 reads the photo, TabNet reads the answers, the backend fuses the scores to say if that pest is likely. FastAPI in Docker, React in four languages. My part: F2.
**How it works**
- **Flow:** pick location (weather panel) → pick pest → photo → 15 questions (each with a reference photo) → Analyze → label, image score, questionnaire score, fused score, annotated overlay (base64), optional Gemini advice.
- **Backend (`models.py`, one `DiseasePredictor` per pest, models loaded once at start-up):** photo → temp file → YOLOv8 via Ultralytics (conf 0.25, IoU 0.45, size 640); Dead Heart = segmentation (masks), Tiller = detection (boxes) per README. **Image score = highest detection confidence.** 15 answers → ones/zeros (yes=1, fixed order) → TabNet (joblib) → probability. **Late fusion: `final = 0.6×image + 0.4×tabnet`, ≥0.5 = positive;** weights/threshold are env variables, in the first commit, **never tuned**.
- **Stack:** Python 3.10, FastAPI + Uvicorn, Ultralytics 8.3, PyTorch CPU-only wheels (smaller image), pytorch-tabnet, joblib, OpenCV + Pillow (overlay), httpx (OpenWeather), optional Gemini · React 18 + Vite, English/Hindi/Tamil/Telugu for the input flow and weather panel · Docker (python 3.10 slim) + compose · stateless, no DB · ~30 MB of models in the repo. **Routes (7):** `/health`; `/weather/current`, `/forecast`, `/disease-risk`, `/disease-risk/{type}`; `POST /predict/deadheart`, `/predict/tiller` (multipart image + questions JSON + language).
- **Weather:** OpenWeather, cached 30 min, hand-written risk rules (forecast days stand in for past days); a separate early-warning panel, **does not change the verdict** (location isn't sent to `/predict`). **Gemini advice:** optional, 4–8 bullets in the user's language, no brands/doses; empty if no key; AI text, not agronomist-verified.
- **Domain:** Dead Heart = dying central shoot of young cane (commonly early shoot borer; general knowledge); Tiller = side-shoot stunting/abnormal tillering.
- **Hardest bug (true, from history):** Dead Heart segmentation failed at prediction with `'Segment' object has no attribute 'detect'`. Scripts (`test_segmentation.py`, `fix_segmentation_model.py`, `fix_model_properly.py`) separated "model file + library" from "my app": predict on a dummy image, read the checkpoint to find the YOLOv8 size, try moving weights to a clean model. History: the model file was replaced and Ultralytics upgraded 8.0.206→8.3.176 next, and I added a fallback so the API doesn't crash. Real ending = F2. The scripts do not prove the cause or test preprocessing/parsing. Lesson: test the model in isolation; pin versions.
- **Choices:** late fusion: models built/replaced separately, no paired dataset needed (cost: scores on different scales, fixed weights; fit them with logistic regression on validation data, pick threshold from a precision-recall curve). YOLOv8: fast on CPU, one library for detect+segment (alt Mask R-CNN). TabNet: the team's model; XGBoost/random forest is a strong simpler baseline for 15 binary features, **not benchmarked: never say TabNet is better**. Segmentation shows exact shape; boxes are cheaper to label. CPU-only PyTorch: free hosts have no GPU. Stateless: nothing to store (alt save cases for retraining).
**Weaknesses (say first, then the fix)**
1. **No accuracy/precision/recall/F1 anywhere**; I won't quote one. Fix: labelled test set, precision/recall/F1 per pest, compare fusion vs image-only vs questionnaire-only; recall matters most.
